# implement_20260725_095558.md

작성 일시: `2026-07-25 09:55:58 KST`

이 문서는 PD20 Iris의 기존 호출어 기반 GLM 자동응답 위에, 안전하게 opt-in 할 수 있는 호출어 없는 일반대화 모드를 추가하기 위한 작업 문서다. 이 기능은 Mac 서버나 프록시에 의존하지 않고 PD20에서 Z.AI GLM을 직접 호출하는 현재 구조를 유지한다.

## 개발 목적

허용된 카카오톡 방에서 사용자가 자신의 대화 세션을 명시적으로 시작한 경우에만, `헤이봇` 호출어 없는 후속 발화를 GLM이 `REPLY`·`WAIT`·`IGNORE`로 판정하게 한다.

공개 오픈채팅에서의 오답·도배·문맥 혼선을 막기 위해 세션 범위는 방 전체가 아닌 정확한 `(chatId, userId)`이며, 운영자는 환경설정으로 기능과 방 범위를 사전 승인한다.

## 개발 범위

- `헤이봇 대화 시작`, `헤이봇 대화 상태`, `헤이봇 대화 종료` 로컬 명령
- 일반대화 전역 기능 플래그와 일반대화 허용 방 allowlist
- `(chatId, userId)`별 process-local 세션, 30분 유휴 TTL, 즉시 종료
- 사용자 4개·성공 전송된 봇 답변 2개의 짧은 세션 문맥
- GLM 단일 호출의 엄격한 `REPLY`·`WAIT`·`IGNORE` JSON arbitration
- 1.5초 debounce, 15초 자동응답 cooldown, 최신 epoch 검증, 성공 전송 뒤에만 답변 commit
- 기존 방별 FIFO scheduler·전체 동시성·중복 방지·호출 제한·봇 에코 방지와의 통합
- 단위 테스트, release APK 빌드, PD20 제한 E2E, 롤백 절차와 운영 문서

## 제외 범위

- Mac `proxy-manager`·이미지·Codex·영상·LAN/ADB transport 개발
- 방 전체 또는 다른 사용자의 일반대화를 자동으로 수집·응답하는 기능
- 일반대화 세션·원문·응답의 디스크 영속화, 장기 아카이브, RAG
- 관리자 채팅 명령으로 사용자 세션을 강제 시작·감시·일괄 변경하는 기능
- GLM 외 다른 LLM provider의 추가 및 기존 호출어 질문 경로의 모델 전환
- 카카오톡 DB schema, Iris `/reply`·`/query` 제어 API 변경

## 현재 기준 상태

- P1 구현으로 호출어 질문은 방별 FIFO queue와 전체 동시성 제한을 사용하며, 대화 기억 키는 `(chatId, userId)`다.
- `BotCommandRouter`는 `헤이봇` 호출어가 없는 메시지에 `null`을 반환하고 `GlmAutoReplyHandler`는 즉시 종료한다.
- 따라서 현재 `안녕` 같은 호출어 없는 입력은 GLM 호출·카카오톡 발신 모두 하지 않는다.
- 관리자 식별은 `/data/local/private/iris-bot-admins.txt`의 숫자 `userId` exact match만 사용한다. 닉네임은 권한 근거가 아니다.
- 일반대화 기능은 아직 구현·배포되지 않았다.

## 결정 기록

| 항목 | 결정 |
|---|---|
| 운영 승인 | `IRIS_GENERAL_CONVERSATION_ENABLED=true`와 일반대화 방 allowlist가 모두 있을 때만 기능을 켠다. 기본값은 OFF다. |
| 사용자 승인 | 일반 사용자는 승인된 방에서만 자기 세션을 시작·상태 확인·종료할 수 있다. 다른 사용자의 세션에는 접근할 수 없다. |
| 관리자 역할 | 관리자 ID는 기존 상태·설정·전체 기억 초기화 권한에만 유지한다. 일반대화의 방 정책 변경은 root 환경설정 변경으로만 수행한다. |
| 세션 키 | `ConversationKey(chatId, userId)` exact match. 같은 방의 다른 참가자 발화는 절대 세션 문맥이나 응답 대상으로 사용하지 않는다. |
| 보관 | 일반대화 세션은 process-local이다. Iris 재시작, `close()`, TTL 만료 시 삭제되며 복원하지 않는다. |
| 기본값 | TTL 30분, debounce 1.5초, cooldown 15초, 사람 4개·봇 2개, 답변 최대 480자. |
| 모델 경로 | 기존 PD20 → Z.AI GLM 직접 호출만 사용한다. 기존 GLM fallback model 설정은 호출 실패 시에만 기존 정책대로 적용한다. |
| 응답 계약 | 정확히 `{"action":"REPLY|WAIT|IGNORE","reply":"..."}` JSON만 허용한다. `WAIT`·`IGNORE`의 `reply`는 반드시 빈 문자열이다. |

### 문서 기반 제약 사항

- 일반대화 후보도 기존 `allowedChatIds`, 텍스트 메시지, 봇 자신의 `userId` 제외 조건을 먼저 통과해야 한다.
- 기존 호출어 명령은 일반대화보다 우선한다. 이미지·관리·기억 초기화·일반 질문을 일반대화 모델에 전달하지 않는다.
- 일반대화에서 나온 메시지 원문, GLM 원문 응답, API key와 Authorization은 로그·metric·상태 응답에 기록하지 않는다.
- GLM 오류, 시간 초과, rate-limit, 잘못된 JSON은 카카오톡 오류 답장을 자동 발송하지 않는다.
- APK 배포·Iris 재기동·실제 카카오방 테스트는 별도 사용자 승인 뒤에만 실행한다.

## Phase 2. 사용자별 세션과 제어 명령

### 목표

현재 방의 현재 사용자만 자신의 일반대화 세션을 시작·확인·종료할 수 있고, 세션은 다른 사용자·재기동·TTL 경계를 넘지 않게 한다.

### 구현 태스크

- [ ] `BotCommand`와 `BotCommandRouter`에 `대화 시작/상태/종료`의 exact command를 추가한다.
- [ ] 공백 정규화 후 exact match만 명령으로 처리하고, 일반 문장 안의 같은 문구는 GLM 질문으로 유지한다.
- [ ] `GeneralConversationSessionStore`를 신규 구현한다. key는 `ConversationKey(chatId, userId)`로 고정한다.
- [ ] 활성 상태, epoch, in-flight, 마지막 활동, 마지막 자동 답장, user/assistant turn deque를 session store가 단독 소유한다.
- [ ] start는 해당 key의 이전 문맥을 지우고 새 epoch를 발급하며, stop·TTL·close는 state와 문맥을 삭제한다.
- [ ] 최대 user 4개·assistant 2개·turn 500자와 30분 유휴 TTL을 적용한다.
- [ ] 일반대화 제어 명령은 GLM queue에 넣지 않고 즉시 짧은 상태 응답을 전송한다.
- [ ] start/status/stop은 feature flag와 일반대화 room allowlist를 모두 검사하며, 미승인 방에서는 세션 상태를 만들지 않는다.

### 자체 테스트

- [ ] 한 사용자의 start/status/stop과 다른 사용자의 상태가 분리된다.
- [ ] 동일 방의 A·B 사용자가 서로의 turns·in-flight·TTL에 영향 주지 않는다.
- [ ] 새 start, stop, TTL 만료, `close()` 뒤에는 호출어 없는 입력이 session snapshot을 만들지 않는다.
- [ ] user 5개·assistant 3개 입력에서 가장 오래된 각 role turn만 제거된다.
- [ ] 공백 변형 제어 명령은 처리하고, 일반 문장 내 포함 표현은 제어 명령으로 오인하지 않는다.

## Phase 3. GLM arbitration·scheduler·안전 발송 통합

### 목표

활성 세션의 무호출어 입력만 기존 GLM scheduler로 처리하고, 모델의 참여 판단과 최신성 검증을 통과한 답변만 한 번 전송한다.

### 구현 태스크

- [ ] `GeneralConversationArbiter`를 구현해 session snapshot을 독립 system prompt와 GLM request로 변환한다.
- [ ] 사람 간 잡담·단순 반응은 `IGNORE`, 미완성 발화는 `WAIT`, 명확한 질문·후속 요청만 `REPLY`로 지시한다.
- [ ] JSON은 정확한 키 집합·문자열 타입·action·reply 길이·`WAIT/IGNORE` 빈 reply 조건을 검증한다.
- [ ] `GlmAutoReplyHandler`에서 호출어 command를 먼저 처리하고, command가 없는 메시지는 활성된 동일 `(chatId,userId)` 세션일 때만 일반대화 후보로 처리한다.
- [ ] 일반대화 요청도 기존 admission controller와 room FIFO scheduler를 공유하되, 질문과 일반대화의 request kind·실행 책임을 명확히 구분한다.
- [ ] 새 입력은 epoch를 증가시킨다. debounce 뒤와 GLM 응답 뒤에 current epoch·active session을 재확인한다.

## 잔여 리스크 / 후속 과제

- 일반대화는 공개방의 발송량과 오답 가능성을 완전히 제거하지 못하므로, 초기는 테스트 방 1개·낮은 rate limit으로 운영 관찰한다.
- `REPLY/WAIT/IGNORE`는 모델 판단이므로 telemetry를 근거로 prompt와 rate limit을 조정할 수 있으나, 기본 동작 변경은 별도 계획으로 관리한다.
- 방 전체 모드, 관리자의 사용자별 강제 승인, 세션 영속화는 개인정보·운영 정책이 달라 현재 범위에 포함하지 않는다.
