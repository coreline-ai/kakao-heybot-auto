# implement_20260806_203913.md

작성 일시: `2026-08-06 20:39:13 KST`

이 문서는 카카오톡 자체 동영상 인코딩이 오래 걸릴 때 DB confirmation timeout을 실패로
오판해 같은 영상을 재전송하거나 불필요한 안내 메시지를 보내는 문제를 수정하기 위한
작업 범위를 고정한다.

## 개발 목적

동영상 direct-share 이후에는 Kakao DB attachment row가 확인되기 전까지 **전송 중/미확인**으로
보수적으로 유지한다. 압축·업로드가 느린 것을 실패로 판단하거나, 앱 재시작·timeout 때문에
같은 영상을 다시 보내지 않는 at-most-once delivery를 만든다.

## 개발 범위

- 생성 영상, 펜브러쉬, 유튜브 다운로드의 MP4 direct-share 공통 문제를 함께 수정한다.
- `startActivity()`까지의 local handoff 성공과 Kakao DB attachment confirmation을 분리한다.
- 파일 크기에 비례한 durable confirmation deadline, silent observation, 상태 조회 문구를 추가한다.
- 앱 재시작 후 이미 handoff된 영상은 **확인만 재개**하고 재전송하지 않도록 한다.
- 수동 재전송은 delayed terminal 상태에서만 1회 허용하고, 처리 중에는 차단한다.
- 기존 v1 job state의 `delivery_pending`/`awaiting_unlock`을 중복 전송 없이 새 processing 상태로 안전하게 migration한다.
- 호출어·도움말·운영 문서·Android 자동 테스트를 동기화한다.

## 제외 범위

- KakaoTalk 내부 encoder 구현·DB schema·비공개 API에 의존한 압축 진행률 추정
- KakaoTalk 화면 자동 조작, Computer Use, 로그캣을 정상 동작 판정의 근거로 사용하는 방식
- 영상 품질/서버 codec 정책 변경, YouTube downloader 정책 변경
- 사용자가 명시하지 않은 실 카카오톡 영상 전송 canary

## 사전 검토 결과 / 결정 기록

| 확인 항목 | 결과와 결정 |
| --- | --- |
| 실기기 증거 | PD20 job state에 `awaiting_unlock`이 남아 있고, Kakao `VideoEncoderThread` stack이 관찰됐다. DB attachment가 없다는 사실만으로 압축 실패를 확정할 수 없다. |
| timeout 오판 | 세 coordinator 모두 45~60초 `deliveryConfirmTimeoutMillis` 후 미확인 안내를 낸다. timeout은 failure가 아니라 `kakao_processing`으로 전환한다. |
| 중복 경로 | 세 coordinator 모두 `pending()`을 startup에 `startPolling()`해 remote `succeeded`이면 다시 `deliver()`한다. handoff 상태는 restart 시 reconciliation만 하도록 분리한다. |
| local handoff | `Replier.sendVideoBytes()`는 enqueue만 하고 caller에 `startActivity()` 성공/실패를 돌려주지 않는다. callback/awaitable handoff receipt를 추가한다. |
| 완료 근거 | bot user의 같은 방 type `3`/`16` Kakao DB row만 delivery completion 근거로 유지한다. logcat/cache/process state는 diagnostics로만 사용한다. |
| 공통 적용 | 생성 영상·펜브러쉬·유튜브가 동일 direct-share/timeout 패턴을 복제한다. 작은 공통 delivery gate를 사용해 방당 동시에 하나의 MP4만 handoff/confirm한다. |
| 대기 정책 | 기본 deadline은 `max(5분, 3분 + ceil(MiB) × 75초)`이며 최대 20분이다. 이 기간에는 자동 재전송·자동 실패 메시지를 금지한다. |

## 공통 진행 규칙

- 각 Phase는 앞선 Phase의 자체 테스트 완료 후에만 시작한다.
- 구현 중 발견한 이슈는 해당 Phase에서 수정하고 문서의 체크 상태를 실제와 맞춘다.
- 신규 사용자 노출 문구는 `HeybotSkillCatalog`·운영 문서·테스트를 같은 변경에서 갱신한다.
- Android 실기기 대상은 PD20 `0123456789ABCDEF`이며 ADB·DB·코드로만 검증한다.
- DB 미확인을 재전송 근거로 사용하지 않는다. 실패는 local handoff 실패 또는 사용자가 명시한 delayed 재시도에서만 처리한다.
- 전송 canary는 사용자 명시 승인 없이는 실행하지 않는다.

## Phase 1. delivery contract·durable processing state

### 목표

카카오 전송 시작과 완료를 분리하고, 앱 재시작에도 재전송하지 않는 상태 계약을 만든다.

### 구현 태스크

- [x] `Replier.sendVideoBytes()`에 `startActivity()`까지 await 가능한 handoff callback을 추가했다.
- [x] 공통 deadline policy와 room-scoped single-flight delivery gate를 구현했다.
- [x] 세 Local job/persisted state에 delivery attempt·handoff 시각·confirmation deadline을 추가했다.
- [x] state document v2와 v1 safe migration을 구현했다. v1의 `delivery_pending`/`awaiting_unlock`은 `kakao_processing`으로 migration한다.

### 자체 테스트

- [x] coordinator dispatch가 local handoff receipt 뒤에만 processing으로 전환되는 것을 회귀 테스트했다.
- [x] 1MiB/14MiB/50MiB deadline 경계 값을 테스트했다. 13.6MiB artifact는 ceil(14MiB) 경로다.
- [x] v1 state migration이 재전송 가능한 `succeeded`로 역전되지 않고 v2로 영속되는 것을 테스트했다.

### 완료 조건

- [x] at-most-once handoff 상태 계약과 migration을 자동 테스트로 고정했다.
